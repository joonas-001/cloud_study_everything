> 确认日期：2026-07-28
> 适用范围：本地单用户验证、算法技能包 `0.2.0` 草稿、受限学习执行预览

## 1. 已确认决定

项目所有者已经确认：

1. 第四里程碑先实施 4A；4B 必须单独确认后才能实施；

4. `0.2.0` 使用全新诊断，不迁移 `0.1.0` 回答；主入口切换到
   `0.2.0`，`0.1.0` 只作为只读历史；
5. `0.2.0` 增加结构化诊断信号，以确定性规则选择补基础活动；自由文本仍不自动判对错；
6. 4A 只收集有限或待复核证据，不能产生当前范围整体达标结论；
7. 4A 只完成算法共同主干入口这一条完整纵向切片；
8. 前三个入口单元各包含学习和一次代表性练习，综合证据检查负责解释、双语言代码文本、迁移、纠错和小作品；

11. 每个技能包精确版本最多存在一个非终态学习执行；初始内容完成后进入
    `retention_pending`，完成规定延迟复测后才能进入 `completed`；
12. 第四里程碑代码实施必须等待第三里程碑 Draft PR 合并，再从更新后的
    `main` 创建实现分支；
13. 第三里程碑远程 CI 已通过，进度文档可以据此同步。
14. `0.1.0` 立即关闭新入口；已有活动诊断和未保存规划冻结为只读，并记录明确原因和审计事件；
15. `0.2.0` 首次被持久化诊断、规划或学习记录引用后禁止原地修改；后续内容变更必须发布新补丁版本；
16. 创建学习执行时允许用户显式选择任意历史 `saved_preview`，但必须提示它可能不再反映最新诊断；
17. 学习执行进入终态后，允许用户明确确认并复用同一不可变规划创建新执行记录；
18. 延迟复习失败后保持 `retention_pending`，追加纠错和新复习；`completed` 只表示本次流程完成，`ended` 不可恢复；
19. 掌握展示拆分为证据等级和待办标记，不能用单一状态覆盖原有证据；
20. 普通自述纠错链只产生有限证据；只有通过确定性预置错误任务才能产生 `supported` 纠错证据；
21. 4A 不提供独立人工审核通过能力；用户依据量表作出的判断仍属于 `self_review`；
22. 4A 的来源变化处理止于确定性元数据差异和 `source_review_pending`，不生成实质影响报告或补充单元；
23. 活动推进采用混合规则：阅读确认即可完成，确定性练习必须通过或完成纠错路径，无法自动判定的文本活动在结构有效提交后可以继续。

4A 中用户提交的代码只作为不可信文本保存，不编译、不解释执行，也不发送给外部 AI。

4B 是独立的隔离代码运行阶段。安装或使用 Docker、WSL，新增运行时依赖，以及任何用户代码执行，都必须在项目所有者再次确认范围后进行。

## 2. 目标

第四里程碑 4A 建立以下最小闭环：

1. 用户完成 `algorithm@0.2.0` 的诊断预览；
2. 用户生成、修改并保存与该诊断绑定的规划预览；
3. 系统从已保存规划创建不可变的学习执行锁；
4. 用户按每日可调整任务完成学习、练习和证据检查；
5. 每次提交、修正、自评和确定性检查都保留历史；
6. 系统按明确量表把证据关联到六个掌握维度；
7. 系统根据真实完成情况安排纠错任务和间隔复习；
8. 学习面板显示当前证据、证据强度、缺口和下一步；
9. 受限预览不得生成正式掌握结论或解锁算法分支。

结构化诊断只能使用明确选项、状态和确定性规则影响活动选择。系统必须显示选择某项补基础活动的原因，允许用户纠正结构化回答，并在回答变化时保留规划变化记录。

本里程碑验证的是通用学习执行引擎，而不是完成整门算法课程。

## 3. 非目标

4A 不实施：

- Docker、WSL、容器或其他用户代码执行环境；
- C++ 编译、Python 执行、性能基准或隐藏测试；
- OpenAI、DeepSeek 或 Moonshot AI 的真实调用；
- 自动评价自由文本是否正确；
- 文件、压缩包或任意本地路径上传；
- 算法四个分支的解锁；
- 整个算法共同主干的完整课程；
- 正式技能包激活；
- “完全掌握”或无限范围的掌握声明；
- 就业、接单、产品化或收入建议；
- 后台常驻调度服务；
- 互联网部署和账号系统。

## 4. 版本与历史边界

### 4.1 保留 `algorithm@0.1.0`

`algorithm@0.1.0` 继续保留在注册表中，维持现有生命周期状态和可用性。其诊断、来源目录和规划模板不再原地修改。

注册表为技能包版本增加与生命周期及 `availability` 正交的
`intake: open | closed`。`0.1.0` 设置为 `intake: closed`，继续允许读取历史内容，但拒绝创建新的诊断、规划或学习执行。

迁移时：

- `0.1.0` 的活动诊断进入 `ended`，结束原因记录为 `version_intake_closed`；
- `0.1.0` 的 `draft` 规划进入只读终态 `frozen_preview`；
- 已保存或已否决规划保持原状态；
- 所有自动转换写入审计事件，不修改回答、规划单元或来源历史。

现有 `0.1.0` 诊断会话和规划预览继续只读可访问。系统不得把它们静默改写为 `0.2.0`，也不得把新内容伪装成原版本内容。

如果 `0.1.0` 出现安全、法律或数据完整性事件，只能使用已确认的 `availability: suspended` 流程，并保留完整审计。

### 4.2 新增 `algorithm@0.2.0`

`algorithm@0.2.0` 保持：

- `state: draft`；
- `availability: available`；
- `intake: open`；
- 只允许本地受限预览；
- 不用于正式计划和分支解锁。

`0.2.0` 必须拥有自己的诊断定义、规划模板、来源目录、学习活动、评估量表和复习策略。

用户需要显式创建全新的 `0.2.0` 诊断预览。系统不得复用或复制
`0.1.0` 的回答。诊断主入口切换到 `0.2.0`，现有 `0.1.0` 记录只能通过只读历史入口查看。

`0.2.0` 在首次被持久化诊断、规划或学习记录引用前可以作为未引用草稿调整。首次引用必须同时保存 manifest 和全部受管内容摘要；从这一刻起，同一版本号的任何摘要变化都必须被应用启动和治理检查拒绝。修复、复习策略变化或教学内容变化必须发布 `0.2.1` 等新版本，不能只依赖记录快照掩盖同版本内容漂移。

### 4.3 不可变学习锁

从已保存规划创建学习执行记录时，必须锁定：

- 诊断会话 ID；
- 规划提案 ID；
- 根技能包 ID 和精确版本；
- 全部传递技能依赖的精确版本和内容摘要；
- manifest 摘要；
- 所有被引用内容文件的路径、种类和摘要；
- 来源目录摘要；
- 规划单元快照；
- 学习活动和量表摘要；
- 引擎协议精确版本；
- Runner 协议版本；
- 运行能力摘要，其中 4A 明确记录 `code_execution: disabled`；
- 创建时间和预览标记。

创建后不得修改学习锁。技能包后续变化只能影响新创建的学习执行记录。

## 5. 共同主干入口纵向切片

4A 只覆盖下列入口范围：

1. 编程基础与双语言表达；
2. 复杂度分析语言；
3. 数组与链式结构；
4. 入口阶段综合证据检查；
5. 延迟复习变体；
6. 错误原因和修正记录。

前三个单元各自只包含来源支持的学习活动和一次代表性练习。综合证据检查负责收集解释、双语言实现文本、迁移、纠错和小作品证据。延迟复习负责产生保持证据。

不得在 4A 中把每个入口单元扩展成各自完整的六维评估闭环。第四里程碑验证的是一条端到端纵向切片，不是完整课程内容量。

同一知识点在 C++ 和 Python 中应说明：

- 语法和表达方式；
- 标准库使用方式；
- 内存和数据结构语义差异；
- 合理的性能差异；
- 当前预览不能通过实际运行验证的部分。

## 6. 技能包内容契约

通用引擎不得硬编码算法题目、答案、量表或复习间隔。建议为技能包增加以下受管内容：

- `learning_definition`：学习单元、活动顺序、先修关系和预计时间；
- `assessment_definition`：任务、允许的提交类型和量表引用；
- `rubric_definition`：标准、证据维度、判定方式和证据强度；
- `review_policy`：复习间隔、失败后处理和策略版本；
- `mastery_scope`：本技能包版本能够评价的明确能力范围。

相应 JSON Schema 必须：

- 禁止未声明字段；
- 使用稳定 ID；
- 校验跨文件引用；
- 校验活动图无断裂和循环；
- 校验每个评估标准至少关联一个掌握维度；
- 校验所有学习活动和评估都能追溯到来源；
- 校验完成标准是可观察的；
- 禁止 4A 声明可执行评分器或运行时配置。

## 7. 学习活动

4A 建议支持以下通用活动类型：

| 类型 | 示例 | 4A 验证方式 |
| --- | --- | --- |
| `study` | 阅读来源支持的概念摘要 | 记录完成，不视为掌握证据 |
| `explanation` | 解释数组和链表的取舍 | 量表引导的用户复核，证据标记为有限 |
| `structured_check` | 排列复杂度或手工跟踪状态 | 确定性答案或结构校验 |
| `code_text` | 提交 C++ 和 Python 实现文本 | 只保存文本，不执行 |
| `transfer` | 为陌生场景选择数据结构并说明理由 | 量表引导的用户复核 |
| `correction` | 修正预置错误案例或自己的原尝试 | 预置错误案例可以确定性检查；普通自述链只验证结构 |
| `project_evidence` | 共同主干入口小作品说明 | 保存结构化说明、反思和代码文本，不接收文件上传 |
| `review` | 延迟出现的概念或迁移变体 | 根据版本化复习策略创建 |

活动完成只表示流程进度。只有满足量表并产生可审查记录的活动才能形成掌握证据。

活动推进规则为：

- `study` 在用户确认阅读后完成，但不产生掌握证据；
- `structured_check` 必须通过，或完成与该失败关联且能够确定性验证的纠错路径后，才能推进；
- `explanation`、`code_text`、`transfer` 和 `project_evidence` 在提交内容通过字段、长度和结构校验后可以推进，但只能形成有限或待复核证据；
- 综合证据检查必须完成全部必需提交和确定性检查，才能把学习执行从 `active` 推进到 `retention_pending`；
- 无法自动判定的文本内容不得因为允许推进就被描述为正确。

## 8. 提交、修正与评估

### 8.1 追加式提交

提交采用追加模式：

- 每次提交生成独立 attempt；
- 已提交内容不可覆盖；
- 修正必须引用被修正 attempt；
- 不再位于当前有效路径的尝试仍保留作审计；
- 草稿可以在提交前修改，但提交后只能新增修订；
- 所有内容长度和结构在 API 边界校验。

### 8.2 评估方式

4A 只允许：

- `deterministic`：结构化题目的确定性结果；
- `self_review`：用户依据明确量表记录的自评；
- `review_pending`：需要未来人工、Runner 或受支持 AI 评估器复核；
- `not_executable`：代码文本未运行，不能证明运行正确。

4A 不创建 `runner`、`ai` 或独立人工审核结果。项目所有者对自己提交内容的量表判断仍记录为 `self_review`，不能伪装成独立人工审核。

### 8.3 证据强度

每条证据至少记录：

- 对应能力范围和标准；
- 掌握维度；
- 来源活动和 attempt；
- 评估方式；
- 结果；
- 证据强度；
- 产生时间；
- 量表版本；
- 是否已被后续修正替代；
- 是否需要延迟复核。

4A 使用以下证据强度：

- `limited`：自评或未执行代码文本；
- `supported`：确定性结构检查，或通过预置错误案例确定性校验的纠错结果；
- `retained_limited`：经过规定间隔后仍能完成代表性任务，但验证方式仍受 4A 限制。

`verified` 和不带限制的 `retained` 保留给未来经过确认的隔离 Runner、受控人工审核或符合规则的 AI 评估。4A 不得产生这两类证据。

用户对自己尝试提交的错误原因和修订文本，即使结构完整，也只能产生 `limited` 纠错证据。共同主干入口的综合证据检查必须包含至少一个带已知错误点和确定性判定规则的预置纠错任务，供用户产生 `supported` 纠错证据。

## 9. 六维证据展示

学习面板分别展示：

- 理解；
- 操作；
- 迁移；
- 作品；
- 保持；
- 纠错。

每个维度拆分为两个正交字段。

证据等级 `evidence_level`：

- `none`：尚无证据；
- `limited`：已有自评、普通纠错链或未执行文本证据；
- `supported`：存在确定性结构检查或确定性纠错任务支持。

待办标记 `review_flags` 可以同时包含：

- `manual_review_pending`：需要未来人工、Runner 或 AI 复核；
- `retention_due`：需要通过延迟复习确认保持；
- `source_review_pending`：来源存在待复核候选。

聚合只使用未被后续修订替代的证据。待办标记不得覆盖或删除既有证据等级；来源候选和复习到期可以与 `limited` 或 `supported` 同时显示。

4A 不提供 `scope_criteria_met` 或任何整体达标状态。聚合只能展示证据等级、待办标记、证据数量和限制，不能单独手工写入“已掌握”。

代码执行被禁用，因此操作、作品和保持维度只能达到有限证据或待复核状态。界面必须持续显示这一限制。

## 10. 复习与每日任务

### 10.1 来源支持的确定性策略

4A 使用简单、可解释、版本化的确定性复习规则，但当前尚未确认具体复习间隔。实施复习调度前必须：

1. 检索同行评审研究、权威教材或专业组织资料；
2. 记录来源、版本或发布日期和检索日期；
3. 尽量使用两个独立高质量来源交叉验证关键结论；
4. 形成候选 `review_policy`，说明规则、适用范围、限制和证据强度；
5. 将策略作为版本化技能包内容接受确定性校验。

发生以下情况时创建更早的纠错或复习任务：

- 结构化检查未通过；
- 用户标记不确定；
- 用户发现原解释或实现存在错误；
- 后续任务暴露前置能力缺口。

来源变化候选只增加 `source_review_pending` 标记，不在 4A 中自动创建教学纠错或复习任务。

首版只允许用户调整每日可用时间，不开放自定义复习间隔。具体间隔和转换规则写入 `review_policy` 后必须测试其确定性；后续修改必须发布新策略版本。

`review_policy` 虽然拥有自己的策略 ID 和版本，但仍属于技能包受管内容。策略变化必须同时发布新的技能包补丁版本；已经创建的诊断、规划和学习执行继续使用原锁定策略。权威来源研究形成候选策略后，必须向项目所有者展示依据、限制和行为影响并获得确认，才能写入待引用的技能包版本。

### 10.2 每日约两小时

每日任务生成器以 120 分钟为目标容量，但不能假设用户每天严格完成。

排序建议为：

1. 到期复习；
2. 阻断后续学习的纠错；
3. 当前单元的核心活动；
4. 非阻断扩展活动。

未完成任务顺延并重新计算，不记录为能力失败。任务调整必须保留变化原因。

4A 不需要后台常驻调度器。用户打开学习页面或开始今日学习时，系统根据当前本地时间和历史完成记录生成队列。

## 11. 数据模型建议

建议通过新的 Alembic 迁移增加：

- `skill_version_content_locks`：技能包版本首次持久化引用时的 manifest 和受管内容摘要；
- `learning_runs`：学习执行记录和状态；
- `learning_run_locks`：不可变版本、内容和协议锁；
- `learning_unit_instances`：规划单元快照及执行状态；
- `learning_activities`：活动实例、顺序和预计时间；
- `activity_attempts`：追加式提交和修订关系；
- `activity_evaluations`：量表版本、方法和结果；
- `mastery_evidence`：维度、标准、强度和来源；
- `mastery_snapshots`：由证据推导的等级与待办标记展示快照；
- `review_tasks`：到期时间、策略版本和状态；
- `learning_events`：创建、提交、修正、评估、重排和结束审计。

建议的关键约束：

- 同一精确技能包版本最多存在一个非终态学习执行记录；
- `(skill_id, skill_version)` 最多存在一个首次引用内容锁，后续加载摘要必须与其一致；
- 学习执行状态使用 `active`、`retention_pending`、`completed` 和 `ended`；
- `active` 与 `retention_pending` 均为非终态；
- 首轮活动完成只能从 `active` 进入 `retention_pending`，不能直接进入 `completed`；
- 只有完成延迟复习并产生相应保持证据后，才能进入 `completed`；
- 延迟复习未通过或用户标记不确定时保持 `retention_pending`，追加纠错活动并根据同一锁定策略创建新的复习任务；
- `completed` 只表示本次学习执行流程完成，不表示任何能力范围已经掌握；
- 用户可以显式结束 `active` 或 `retention_pending` 记录，使其进入不可恢复的 `ended`，但不得删除历史锁、尝试、评估、证据和审计事件；
- `completed` 或 `ended` 后，用户可以明确确认并复用同一 `saved_preview` 创建新执行记录；新记录必须拥有独立 ID、不可变锁和审计链；
- 学习执行必须引用 `saved_preview` 状态的规划；
- 学习锁创建后不可更新；
- attempt 修订号在同一活动内唯一；
- evidence 必须引用 evaluation 和 attempt；
- review task 必须记录策略版本；
- 状态字段使用数据库约束；
- 删除学习执行记录不得级联删除仍被审计引用的版本锁。

具体表结构应在实施前通过迁移设计和测试再次审查。

## 12. API 边界建议

建议增加：

- `POST /learning-runs`
- `GET /learning-runs/active?skill_id={skill_id}&skill_version={skill_version}`
- `GET /learning-runs/{run_id}`
- `POST /learning-runs/{run_id}/today`
- `POST /learning-activities/{activity_id}/attempts`
- `POST /learning-activities/{activity_id}/attempts/{attempt_id}/corrections`
- `POST /activity-attempts/{attempt_id}/self-review`
- `GET /learning-runs/{run_id}/evidence`
- `GET /learning-runs/{run_id}/reviews`
- `POST /review-tasks/{review_id}/start`
- `POST /learning-runs/{run_id}/end`

所有学习执行响应必须明确包含：

- `is_preview`；
- `code_execution`；
- 技能包和策略版本；
- 当前证据限制；
- 是否存在待人工复核；
- 证据等级和可并存的待办标记；
- 所选规划是否早于最新诊断或规划；
- 下一步允许的操作。

创建学习执行时必须拒绝：

- 未保存、已否决、已冻结或不存在的规划；
- `0.1.0` 规划被请求为 `0.2.0` 学习记录；
- 技能包不可用；
- 技能包版本 `intake` 已关闭；
- 内容摘要或注册表不一致；
- 非本地供应商；
- 试图开启代码执行或外部 AI；
- 已存在非终态学习执行记录。

用户可以显式选择同一精确技能包版本下任意历史 `saved_preview`，不要求它属于最新诊断。响应和确认界面必须展示该规划绑定的诊断时间、规划保存时间、是否存在更新的诊断或规划，以及尚未解决的来源候选。历史规划仍然锁定其原诊断，不得重新绑定；用户的显式选择和过时提示必须写入学习执行审计事件。

## 13. 来源变化对学习证据的影响

来源检查产生候选变化时，4A 只生成确定性元数据差异，并为受影响标准追加 `source_review_pending` 标记。它不得立即改写学习锁、活动、attempt、评估、既有证据或证据等级。

用户接受来源变化候选，只表示确认候选值得后续复核。由于 4A 禁止外部 AI，也没有独立人工内容审核能力，因此 4A 不生成实质内容影响报告、补充学习单元或版本迁移。

未来只有在经过确认的 AI 或独立人工审核流程能够说明变化内容、必要性、工作量和建议插入位置，并再次取得用户确认后，才能发布新技能包版本、创建版本锁定的补充学习单元或执行显式迁移。原始内容、证据、候选、用户决定和全部审计记录必须保留。

用户拒绝候选时，同样保留决定和原因。任何来源变化都不能静默提升或降低掌握判断。

## 14. 前端流程

学习面板建议按以下顺序呈现：

1. 今日任务与预计总时长；
2. 当前活动和安排原因；
3. 完成标准与量表；
4. 提交、修正或自评操作；
5. 本次产生的证据；
6. 六维证据状态；
7. 来源与版本锁；
8. 下一次复习。

必须覆盖：

- 没有 `0.2.0` 诊断；
- 诊断仍在进行；
- 没有已保存规划；
- 选择历史规划及其过时提示；
- 学习执行尚未创建；
- 今日没有到期任务；
- 提交成功和失败；
- 证据待复核；
- 同时存在证据等级和多个待办标记；
- 延迟复习未通过后仍处于 `retention_pending`；
- 终态后明确确认并复用规划；
- 代码执行关闭；
- 来源失败、待复核或发生变化；
- 技能包 suspended；
- 桌面和移动布局；
- 键盘操作、焦点、`aria-live` 和减少动效。

界面不得使用单一绿色勾选或百分比表示整项能力已经掌握。

## 15. 隐私与安全

4A 的边界：

- 所有数据保存在本地 SQLite；
- 不向外部 AI 发送活动、回答或代码；
- 不读取用户任意本地路径；
- 不接收文件上传；
- 不执行代码；
- 不把代码传给 FastAPI 动态导入、`exec` 或子进程；
- 输入、技能包内容和来源元数据均视为不可信；
- API 限制文本长度和允许字段；
- 日志只保存必要的结构化事件，不复制完整代码和敏感内容。

4A 不增加持续 API 费用。SQLite 数据量会随尝试和审计历史增长，但当前单用户范围内优先保留可追溯记录。

## 16. 验证与 CI

第四里程碑实施时至少增加本地检查：

- `check:learning-content`：学习定义和活动图；
- `check:assessment`：任务、量表和证据维度；
- `check:review-policy`：复习策略和确定性转换；
- `check:mastery-policy`：聚合状态不得越权声称掌握。

相应 GitHub Actions 稳定检查建议为：

- `curriculum-graph`
- `assessment-contract`
- `mastery-policy`

这些检查必须先有本地等价命令，再进入 CI 和 `release-readiness`。

自动化测试至少覆盖：

- `0.1.0` 关闭新入口，活动诊断和草稿规划冻结且历史内容不漂移；
- `0.2.0` 首次持久化引用后，同版本内容摘要变化被拒绝；
- `0.2.0` 注册表、内容摘要和跨文件引用；
- 任意历史 `saved_preview` 可以被显式选择，过时提示和选择审计完整；
- 学习锁不可变；
- attempt 追加修订；
- 修正链和旧证据保留；
- 完成活动不等于满足掌握标准；
- 4A 不会生成 `scope_criteria_met`、`verified` 或不受限的 `retained`；
- 六维证据等级和多个待办标记独立聚合且互不覆盖；
- 普通自述纠错只产生有限证据，确定性预置错误任务才能产生支持证据；
- 4A 的 `self_review` 不能写成独立人工审核结果；
- 代码文本不执行；
- 首轮活动完成进入 `retention_pending`，只有延迟复习后才能完成；
- 延迟复习失败保持 `retention_pending` 并追加纠错和复习任务；
- 同一精确技能包版本只能存在一个 `active` 或 `retention_pending` 学习执行；
- 显式结束学习执行后保留所有历史；
- 终态后可以在明确确认下复用同一规划创建独立新记录；
- 不同活动类型按照已确认的混合推进规则执行；
- 复习间隔和错过任务后的重排；
- 4A 来源变化只产生确定性元数据差异和待办标记，不生成实质影响报告或补充单元；
- 数据库升级和降级兼容；
- OpenAPI 和 TypeScript 契约无漂移；
- 桌面和移动端完整 E2E；
- 测试退出后不残留服务、进程或监听端口；
- 完整本地 `release-readiness`；
- 推送后的远程 GitHub Actions。

## 18. 4A 完成标准

只有同时满足以下条件，才能称 4A 实现完成：

- `algorithm@0.2.0` 草稿通过所有仓库治理检查；
- `0.1.0` 新入口关闭，活动记录安全冻结，内容和历史引用保持不变；
- `0.2.0` 首次持久化引用后不能原地修改；
- `0.2.0` 必须完成全新诊断，结构化诊断信号以确定性规则影响补救活动，并展示安排原因；
- 可以显式选择 `0.2.0` 的任意历史已保存规划，并在过时提示后创建不可变学习执行锁；
- 可以完成一条共同主干入口纵向切片；
- 首轮活动完成后进入 `retention_pending`，延迟复习成功后才能结束为 `completed`；
- 延迟复习失败保持待复习状态，终态后可以明确确认并复用规划；
- 尝试、修正、评估、证据和复习记录可追溯；
- 六维证据等级与待办标记独立展示，不会把完成进度包装为掌握；
- 普通自述纠错和用户自评不会被包装成确定性或独立人工审核证据；
- 来源变化不会在 4A 中生成实质影响报告、补充单元或迁移；
- 4A 不产生整体范围达标、已验证代码能力或不受限保持证据；
- 所有代码提交明确标记为未执行；
- 没有外部 AI 请求；
- 没有文件上传和任意本地路径读取；
- 桌面、移动、空、加载、错误和受限状态通过验证；
- 本地与远程全部必需检查成功。

“4A 实现完成”不表示算法技能包已经激活，也不表示用户已经掌握算法共同主干入口。
