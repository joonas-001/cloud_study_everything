## 1. 里程碑结论

第八里程碑建议命名为“算法学习内核完整化”。它优先解决 GitHub 同类项目差距分析中的
`GAP-P0-01` 至 `GAP-P0-05`：

1. 把算法共同主干从入口纵向切片扩展为可实际连续学习的版本化路径；
2. 把固定问题序列升级为透明、可解释、可回退的确定性自适应诊断；
3. 建立范围化能力档案，让证据可理解、可导出、可交给真人按受管量表复核；
4. 建立不把停留时长或完成率冒充掌握的学习效果分析；
5. 为未来个体化复习建立影子评估和校准门禁，不在数据不足时直接替换固定策略；
6. 建立低摩擦、可脱敏、可追溯的 GitHub Issues 反馈和发布验证闭环。

第八里程碑不接入真实 AI 导师、不做 PDF 或任意文件导入、不建设富文本编辑器，也不增加
多用户、支付、证书、产品内公开社区、开放注册或教育机构集成功能。这些能力属于 P1/P2
或与当前产品决定冲突，应留在后续独立里程碑和授权中。仓库 GitHub Issues 只用于项目维护，
不表示产品已经公开上线或建立用户社区。

## 2. 制定依据

### 2.1 当前能力基线

`algorithm@0.2.2` 当前只有四个学习单元：

- 编程基础与双语言表达；
- 复杂度分析语言；
- 数组与链式结构；
- 入口阶段综合证据检查。

它已经证明以下基础设施可用：

- 不可变技能包、manifest 和受管内容摘要；
- 确定性诊断补救映射；
- 学习执行状态机、追加式提交和历史审计；
- 六维证据、待办和证据等级分离；
- C++ 与 Python 的锁定 Runner 验证；
- 固定延迟复习和同范围 Runner 复测；
- 桌面、移动、私有部署、备份与发布门禁。

但它明确只是纵向切片，不能据此声称共同主干已经完整、四个分支已经解锁或用户已经掌握
算法。

### 2.2 同类项目启示

## 3. 目标

### 3.1 产品目标

第八里程碑完成后，用户应能：

1. 在新算法技能包版本上重新完成编程、数学和算法前置诊断；
2. 获得解释“为什么问下一题、为什么停止、为什么需要补救”的诊断结果；
3. 按每天约两小时、可延期且可重排的任务连续学习共同主干；
4. 使用 C++ 为主、Python 为辅完成来源支持的练习、确定性代码任务和迁移任务；
5. 查看每个能力范围的证据、时效、验证方式、待办和限制；
6. 导出本地能力档案供自己复盘或交给外部真人评审；
7. 查看尝试、纠错、Runner 验证、延迟复测和证据过期的趋势，但不会看到伪造的掌握百分比；
8. 在数据不足时继续使用已确认固定复习策略，同时让候选自适应模型只在影子模式评估。

### 3.2 工程目标

- 通用学习引擎不得硬编码算法单元或能力 ID；
- 新技能包版本不得修改 `0.1.0`、`0.2.0`、`0.2.1` 或 `0.2.2`；
- 所有新能力、单元、活动、题目、Runner 任务、量表和来源必须进入版本化契约；
- 诊断选题和停止决定必须确定性重放并保留原因；
- 证据聚合必须按精确技能版本、能力范围、验证方式和时效计算；
- 历史记录继续可读，不因新版本发布自动迁移、降格或抬高；
- 本地和 CI 继续调用同一组仓库命令；
- 不增加外部调用、云资源或持续费用。

## 4. 非目标

第八里程碑明确不包含：

- OpenAI、DeepSeek、Moonshot AI 或其他真实 AI 学习对话；
- PDF、Word、网页、视频或用户任意本地路径导入；
- AI 自动生成并直接发布课程、练习、答案或能力依赖；
- 富文本块编辑器、实时协作、班级、组织、多租户和复杂 RBAC；
- 自动证书、排行榜、论坛、社交、支付、课程售卖或 SEO；
- LTI、SCORM、xAPI 或外部 LMS 集成；
- 自动投递、联系、发布、签约、交易或其他外部动作；
- 自动启用接单或产品化实验；
- 公开互联网访问、开放注册、域名购买、扩容或新增付费资源；
- 以浏览时长、任务完成、单次测验、AI 评价或自评直接声明掌握；
- 在未校准前向用户显示“记忆率”“掌握概率”等伪精确指标。

## 5. 建议的共同主干范围

共同主干应覆盖四个未来分支共享的基础，避免在工程、面试、竞赛和理论分支中重复教学。
建议建立以下十二个能力域；精确单元数和题量在 8A 确认：

| 能力域 | 最小范围 | 代表性可观察证据 |
| --- | --- | --- |
| P：双语言编程基础 | C++ 基础、STL、Python 容器、函数、输入输出、边界和复杂度差异 | 双语言小程序、边界测试、实现差异解释 |
| M：必要数学与逻辑 | 命题逻辑、集合、函数、归纳、求和、对数、基础组合与概率 | 确定性题、推导步骤、算法分析中的应用 |
| A：算法分析与正确性 | 渐近分析、最坏/平均情况、循环不变量、归纳证明、时间与空间 | 复杂度推导、反例、正确性说明 |
| L：线性结构 | 数组、链表、栈、队列、双端队列 | 结构选择、Runner 实现、迁移任务 |
| H：哈希与集合 | 哈希表、冲突、负载、集合和映射语义 | 方案选择、实现、复杂度条件说明 |
| S：搜索与排序 | 二分、基础排序、比较排序、稳定性、下界直觉 | Runner 测试、排序选择和反例 |
| R：递归与分治 | 递归状态、递推式、分治设计、栈风险 | 递归/迭代实现、递推分析、边界处理 |
| T：树与堆 | 二叉树、遍历、BST、堆、优先队列 | 遍历与堆操作、结构不变量解释 |
| G：图基础 | 表示、BFS、DFS、拓扑、最短路与最小生成树的适用条件 | 图建模、Runner 实现、算法选择 |
| Y：贪心 | 贪心选择、交换论证、反例 | 正确性论证和失败策略纠错 |
| D：动态规划 | 状态、转移、边界、顺序、空间优化 | 状态设计、双语言实现、迁移任务 |
| Q：综合建模与质量 | 问题建模、测试、调试、性能测量、代码可读性 | 综合作品、变体任务、外部真人量表 |

范围控制规则：

- 每个域只教授四个分支共同需要的内容；高级竞赛技巧、工程框架、面试套路和理论深化留在分支；
- 数学只按算法需要补充，不建立脱离任务的完整数学课程；
- 每个能力域至少包含学习、主动提取、确定性练习、迁移或作品、纠错和延迟保持路径；
- 不是每项自由文本都能自动判对。只有确定性结构、锁定 Runner 或受管真人评审才能产生相应
  `supported`、`verified` 或 `retained` 证据；
- 分支解锁必须依赖明确能力范围和阶段门禁，不能依赖总进度百分比。

## 6. 技能包与版本策略

### 6.1 推荐方案

建议把扩展后的共同主干发布为 `algorithm@0.3.0` 草稿，原因是它不是对 `0.2.2` 的小范围
来源修复，而是能力图、诊断、课程、评估和学习执行范围的明显扩展。

`0.3.0` 仍然是草稿，不因版本号变化自动表示正式、完整或已验证。只有满足第 15 节完成
标准后，才能由项目所有者决定是否把新诊断、规划和学习入口切换到该版本。

### 6.2 历史处理

- `0.1.0` 至 `0.2.2` 保持字节和摘要不可变；
- 既有诊断、规划、学习、证据、实验和市场研究继续绑定原精确版本；
- `0.2.2` 已开始或已完成的学习执行不自动迁移；
- 用户选择 `0.3.0` 时必须重新诊断；
- 旧版本的历史记录继续可读，不因新版本出现而变成错误或失效；
- 如需复用旧规划或证据，只能按已有规则显示其版本、时间和限制，不能复制成新版本证据；
- `0.3.0` 首次被持久化记录引用后立即锁定，后续内容变化发布 `0.3.1` 或更高新版本。

### 6.3 内容来源

- 每个能力域至少有一个直接支持教学结论的权威或高质量来源；
- 语言语义优先使用 Python、ISO C++ 或实现文档等一手来源；
- 算法教学可使用公开大学课程、正式教材开放版本、标准组织和高质量学术资料；
- cppreference 继续标为社区维护参考资料，不能改写为官方标准；
- GitHub 同类项目只能提供产品方法，不能替代算法内容来源；
- 不复制候选项目课程、题目、答案、测试、设计资产或代码；
- 来源变化仍先生成待审差异，不能原地修改已锁定技能包。

## 8. 8A：能力图与内容规格

8A 是第八里程碑唯一可以在不接触生产运行能力的前提下先行制定的阶段。建议交付：

1. 十二个能力域的能力 ID、定义、前置依赖和不包含范围；
2. 每个能力范围的诊断信号、补救规则和继续学习阈值；
3. 学习单元、活动类型、来源、完成标准和证据维度覆盖矩阵；
4. C++ 与 Python 的实现差异清单及必须使用 Runner 的范围；
5. 每天约两小时的任务拆分规则、逾期和动态重排规则；
6. 阶段检查点和四分支解锁所需能力范围；
7. 内容规模预算，防止一个技能包版本大到无法审核；
8. 内容准确性、题目歧义、Runner 测试和量表的抽审方案；
9. `algorithm@0.3.0` manifest、schema 和历史迁移的差异设计；
10. 8B–8G 的实施量、风险、费用和停止条件。

8A 不创建真实学习记录、不切换默认入口、不修改数据库、不调用外部 AI、不安装新依赖，且
不能把能力图“设计完成”解释为课程内容已经完成。

8A 已形成 `docs/architecture/milestone-8a-learning-core-spec.md` 和机器可检的
`docs/architecture/milestone-8a-spec.json`。精确能力 ID、前置图、单元、预算、诊断信号、
来源矩阵和延期任务以机器规格为 8A 真值；8B 实施前仍须单独授权并重新核验候选来源。

## 9. 8B：技能包与内容底座

8B 在取得单独授权后，根据 8A 已确认规格建立不可执行或未开放入口的新技能包草稿：

1. 为能力节点、前置依赖、诊断题目元数据和活动覆盖增加通用契约；
2. 创建 `algorithm@0.3.0` 目录、manifest、来源目录、诊断题库、学习单元、评估、量表和
   Runner 任务定义；
3. 按 8A 的内容预算分批编写和审查，但在内容完整并锁定前不允许真实诊断、规划或学习记录
   引用该版本；
4. 为十二域分别建立来源、主动提取、确定性练习、纠错和延迟保持路径；
5. 为需要执行的 C++ 与 Python 任务固定运行时、精确镜像摘要、测试集合和能力范围；
6. 增加内容覆盖、依赖图、题目歧义、答案一致性、Runner 契约和算法硬编码检查；
7. 默认入口继续指向现行允许版本，8B 完成不自动开放 `0.3.0`；
8. 不从 GitHub 候选项目复制课程、题目、答案、测试或代码。

内容结构校验只能证明受管文件符合契约，不能证明自由文本教学解释全部正确。8B 必须记录
来源复核和内容抽审结果，尚未复核的内容保持明确待办，不能被治理检查的成功覆盖。

## 10. 8C：确定性自适应诊断设计

### 10.1 题目元数据

每个诊断题至少记录：

- 精确技能包版本和题目版本；
- 能力范围与前置能力；
- 难度档位和题型；
- 可观察信号及其证据限制；
- 正确、错误、跳过、不确定和修正分别如何更新状态；
- 选择该题的可解释原因；
- 来源、答案、反馈和歧义审查状态；
- 是否允许作为提前停止依据。

### 10.2 选题规则

首版推荐确定性规则引擎，而不是 LLM：

1. 先问会阻断多数后续域的编程、数学和复杂度题；
2. 在某能力状态不确定时优先选择能区分“需补救”和“可继续”的题；
3. 已由足够独立信号确认的能力不重复提问；
4. 用户修正答案后，从受影响能力和所有下游依赖重新计算；
5. 跳过和不确定不能当作错误，但会保留 `inconclusive` 或补充提问；
6. 达到时间或题量上限时停止，并明确显示哪些能力仍无法判断；
7. 规则无法选择安全下一题时退回受管固定序列，不猜测也不调用外部模型。

### 10.3 停止条件

只有同时满足以下条件之一才可结束：

- 所有入口必需能力均已被分类为 `ready`、`remediation_required` 或明确的 `inconclusive`；
- 达到项目所有者确认的时间或题量上限；
- 用户主动结束；
- 会话超时或发生既有致命异常。

诊断输出只能表示“当前路径决策的可用信号”，不能产生 `verified`、`retained` 或整体掌握。

## 11. 8D：学习执行与分支门禁

### 11.1 每日任务

- 默认任务预算约 120 分钟；
- 实际完成少于计划时，未完成任务可追加式延期并重新排序，不把延期记为能力失败；
- 每日优先级依次为到期保持、失败纠错、当前前置能力、正常新内容；
- 不在同一天堆叠多个高认知负荷新域；
- 用户可以暂停、结束或选择历史精确规划，历史和原因必须保留。

### 11.2 活动与证据

| 活动 | 最低完成规则 | 可产生的最高自动证据 |
| --- | --- | --- |
| 阅读或演示 | 用户确认 | 不因确认产生正确性证据 |
| 确定性选择/结构题 | 精确规则通过或受管纠错通过 | `supported`，仅限题目能力范围 |
| C++/Python 代码 | 锁定 Runner 和完整确定性测试通过 | `verified`，仅限任务操作范围 |
| 解释、证明、迁移、作品文本 | 结构有效后可继续 | 未经真人评审不能声称内容正确 |
| 受管外部真人评审 | 当前量表、范围、关系、结论和日期有效 | 按既有策略形成相应独立验证记录 |
| 延迟复测 | 同范围、同运行时边界的 Runner 或受管复核通过 | `retained`，仅限相应能力范围 |

### 11.3 分支解锁

8D 只建立分支门禁和准确入口，不要求在第八里程碑内完成四个分支内容。分支入口必须：

- 显示所需共同主干能力范围；
- 分开显示现有证据、过期证据、待复核和缺失能力；
- 不要求所有能力都达到同一证据等级，但规则必须版本化并可解释；
- 不能因为基础设施 Runner 探针成功而解锁用户能力；
- 不能因为整体学习执行 `completed` 而自动解锁；
- 用户未选择就业、竞赛、理论或工程目标时，不默认替用户选择分支。

## 12. 8E：能力档案、分析和复习影子评估

### 12.1 范围化能力档案

能力档案建议包含：

- 技能、精确版本、能力范围和人类可读名称；
- 证据维度、等级、产生方式、日期、有效期和验证者类型；
- Runner 协议、运行时版本和镜像摘要，但不包含用户密钥或敏感正文；
- 关联任务、测试范围、纠错、迁移、作品和延迟复测；
- 人工、保持、来源和版本待办；
- “能证明什么”和“不能证明什么”；
- JSON、CSV 和本地打印视图导出。

不得生成不带范围和限制的“算法大师”“已完全掌握”或自动证书。默认不创建公开链接。

### 12.2 学习效果分析

允许展示：

- 每个能力范围的尝试、成功、失败、不确定和纠错次数；
- 从首次学习到确定性通过、从失败到纠错通过的时间；
- 到期、逾期、通过和失败的延迟复测；
- 证据等级、时效和阻断原因变化；
- 计划任务与实际完成的偏差，用于重排而非惩罚。

禁止展示或推断：

- 用页面停留时长、点击量或内容完成率计算掌握；
- 没有校准依据的学习效率排名、智力评分或成功概率；
- 用收入、求职结果或外部动作反推掌握；
- 用跨技能或跨版本记录静默合并成一个百分比。

### 12.3 复习候选影子评估

第八里程碑推荐只做影子评估：

- 已确认的固定 `1、2、4、7、15` 天策略继续决定真实任务；
- 候选模型读取最少的本地复习结果，输出不影响任务和证据的内部预测；
- 用户界面不展示未经校准的记忆概率；
- 预先定义比较指标、最小样本、冷启动、缺失数据和失败回退；
- 候选模型、参数、输入字段和代码版本全部锁定；
- 样本不足时结论固定为 `insufficient_data`；
- 只有完成离线校准报告并取得项目所有者新授权，未来技能包版本才能切换策略。

## 13. 8F：GitHub Issues 反馈与发布准备

8F 参考 `xingkongliang/skills-manager@8f34bf1` 的低摩擦反馈方法，但按云奕学的证据、隐私、
授权和单用户边界重新设计。详细核验见 `docs/research/github-issues-workflow.md`。

### 13.1 提交入口

建议使用三个 GitHub Issue Forms：

| 类型 | 必填重点 | 自动标签 |
| --- | --- | --- |
| 缺陷报告 | 发生了什么、期望行为、最小复现、影响、版本、脱敏诊断 | `type:bug`、`status:needs-triage` |
| 功能或改进 | 要解决的问题、理想行为、现在为什么需要、边界冲突、验收标准 | `type:enhancement`、`status:needs-triage` |
| 内容或证据问题 | 精确技能版本、能力/活动/来源 ID、问题类型、最小证据、期望处理 | `type:content`、`status:needs-triage` |

空白 Issue 默认关闭。安全问题不得创建公开 Issue，应由 `SECURITY.md` 引导到 GitHub Private
Vulnerability Reporting。单用户阶段不要求开启 Discussions；不确定是否为 Bug 时仍可提交，
分诊后再改变类型。

### 13.2 应用内四步流程

```text
设置 → 系统状态 → 报告问题
  → 本地生成允许列表诊断
  → 用户预览、删除可选字段并确认复制
  → 打开预填 GitHub Issue，由用户自行检查和提交
```

系统不得自动创建、提交、评论或上传 Issue。打开浏览器属于用户明确触发的外部动作；失败时
只保留本地可复制文本，不静默重试。

### 13.3 诊断允许列表和禁止内容

允许字段仅包括应用版本/提交、非识别性系统摘要、Web/API 健康、数据库 schema revision、
页面路由、操作类型、精确技能包版本、Runner 协议/运行时/启用状态、功能开关状态、请求审计
ID、原因码、时间和受管结构化事件名称。

以下内容不得进入 Issue、截图、剪贴板诊断或附件：

- 凭据、用户名、邮箱、Microsoft/GitHub/Tailscale 身份、私有 IP/URL 和任意本地路径；
- 诊断回答、学习答案、代码、作品、迁移任务、证据正文和真人评审敏感材料；
- AI 提示/响应、市场摘录、收入金额、合同、账单和银行材料；
- SQLite 数据、备份密钥、原始日志、崩溃内存转储和基础设施秘密。

首版不提供完整日志 zip 上传。诊断外发前必须完整预览，用户可以删除所有可选字段；关闭
外部发送不妨碍生成本地诊断，但不得绕过用户选择打开或提交 GitHub 页面。

### 13.4 标签、里程碑和生命周期

受管标签至少包含类型、状态、优先级、区域以及 `known-issue`、`duplicate`、`regression`。
标签语义和颜色需要版本化记录，避免参照项目样本中出现的功能请求误标为 Bug 等漂移。

```text
needs-triage
  → needs-info / duplicate / rejected-with-reason
  → accepted
  → blocked / in-progress
  → needs-verification
  → closed
  → regression 时 reopen
```

- 提交前搜索标题、原因码和能力/活动 ID；
- 重复问题关联原 Issue，不通过重建丢失上下文；
- `needs-info` 14 天无补充可人工关闭并保留 reopen；首版不做定时自动关闭；
- 被接受的实施 Issue 必须绑定 GitHub Milestone、`TODO.md` 编号和精确阶段；
- `accepted` 不等于获得实施授权，GitHub Issue 不能扩大 `AGENTS.md` 或 `TODO.md` 的范围；
- PR 可使用 `Closes #...`，但合并前必须有测试、验收证据和限制说明；
- 缺陷再次出现时优先 reopen 并标记 `regression`。

### 13.5 8F 交付物

- 三个 Issue Forms 和关闭空白 Issue 的配置；
- `SECURITY.md` 与私密安全报告入口；
- 中英双语置顶“如何提交高质量问题”指南；
- 受管标签字典、GitHub Milestone 和 TODO 映射规则；
- 应用内可预览、可删字段、只复制不提交的脱敏诊断；
- Bug、功能、内容/证据三条自动化流程测试；
- 重复、needs-info、reopen、PR 关闭和发布验证规则；
- 证明诊断不含禁止字段的负面测试和密钥扫描。

创建远程标签、GitHub Milestone、置顶 Issue、开启 Private Vulnerability Reporting 或提交真实
测试 Issue 都是外部写操作。8F 代码授权本身不自动授权这些动作，实施时必须再次明确确认。

```text
  → 8G 完整验收与入口决定
```

发生以下任一情况应停止当前阶段并报告：

- 必要 Python 依赖不支持 Python 3.14.3；
- 需要更改 Node.js 24、pnpm、uv 或 Runner 安全基线；
- 发现必须调用外部 AI、远程来源或新增付费资源才能继续；
- 新内容缺少可接受来源或许可证边界不清；
- 通用引擎不得不硬编码算法能力；
- 需要修改已被引用技能包的字节或摘要；
- 历史记录无法无损保留或数据库迁移无法可靠回滚；
- 自适应规则无法解释或无法确定性重放；
- 候选复习模型样本不足、无法估计或校准失败；
- 能力档案会泄露敏感正文、凭据、金额或产生误导性掌握结论；
- Issues 诊断、截图或附件会泄露学习正文、代码、凭据、私有地址、金额或本地路径；
- 需要未经确认地创建远程标签、Milestone、Issue、评论或修改 GitHub 仓库设置；
- 真实 Runner 安全矩阵、资源余量、容器清理或回滚能力失败。

| Tailnet 私有候选 | 8F 完成且 8G 上线预检通过；另行取得部署授权 | 单账号白名单、功能开关默认关闭、加密备份、可回滚候选 | 公开访问、扩容、真实 AI、邮件或未授权来源访问 |
| 私有默认版本 | 候选观察和验收通过；项目所有者明确确认 | 将新诊断/规划/学习入口切换到 `0.3.0`，旧版本继续服务历史 | 把切换解释为用户掌握或公开发布 |

推荐私有候选至少观察 14 天，并真实覆盖：一次完整诊断、一次规划保存、至少两个能力域、
一次 C++ 和一次 Python Runner、一次失败后纠错、一次延迟复测、一次能力档案导出以及一条
从报告到验证关闭的 Issue 流程。时间达到但覆盖不足时不能仅凭“运行了 14 天”通过；覆盖
完成且出现 P0 数据、安全、证据或回滚问题时也不能通过。

### 18.3 公开上线

不建议在第八里程碑结束时直接公开上线。公开上线至少需要另立“公开发布准备”门禁并确认：

- 产品目标从单一所有者扩展到哪些用户，是否允许注册以及谁负责支持；
- 身份、访问控制、Runner 滥用防护、配额、限流和数据隔离；
- 隐私政策、服务条款、内容与第三方许可证、删除和数据导出；
- 安全报告、漏洞响应、日志、监控、备份和灾难恢复责任；
- 外部 AI、来源、邮件和持续费用预算，或明确继续关闭；
- GitHub Issues/安全报告的维护能力和响应规则；
- 至少 30 天私有日常使用中没有未解决的 P0/P1 数据丢失、安全、证据误判或回滚问题。

因此，最合适的节奏是：8G 后先做 14 天私有候选，再决定是否切换个人默认版本；公开上线
不绑定某个日期，也不因第八里程碑完成自动发生。

## 19. 与后续里程碑的建议边界

如果第八里程碑完成，后续可再单独讨论：

- 第九里程碑：个人知识工作台，包括受管笔记、标注、检索、内容导入研究和知识图谱展示；
- 第十里程碑：真实 AI 学习辅导，包括供应商模型确认、费用、隐私、会话协议和内容复核；
- 算法分支里程碑：工程、面试、竞赛和理论四个分支逐个发布，不同时堆叠；
- 只有出现真实需求后，再评估 PWA、教育标准、公开分享或第二技能。

这些只是边界建议，不构成第九、第十或分支里程碑的立项和实施授权。
